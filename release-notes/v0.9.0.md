## Upgrade

Run the installer again on each machine, and on the machine that runs your
server:

```bash
curl -fsSL https://github.com/l7aromeo/user-memory/releases/latest/download/install.sh | sh
```

On Windows, in PowerShell:

```powershell
irm https://github.com/l7aromeo/user-memory/releases/latest/download/install.ps1 | iex
```

- **The store's format changes, from schema version 5 to 6.** 0.9 replaces
  an unused copy of every memory's text with a keyword index of each
  memory's stems. The installer first backs the store up beside it, as
  `<store>.v5-<UTC time>.bak`, then migrates it in one transaction. No
  memory, conversation or vector changes. A store of 20,000 memories took
  under a second, and one of 100,000 from 5 to 16 seconds.
- The installer's Docker server upgrades as it did for 0.8: the installer
  builds the new image, checks the store, stops the server, backs the
  store up and migrates it inside the volume, then starts the server again.
- A 0.8 binary refuses a version 6 store, so upgrade every machine that
  opens it, the server's included. To go back to 0.8, restore the
  `.v5-<time>.bak` backup and reinstall 0.8.1, as
  [roll back an upgrade](https://github.com/l7aromeo/user-memory/blob/main/docs/upgrade.md#roll-back-an-upgrade)
  describes. Memories recorded since the upgrade are lost unless you export
  them first.
- A server run from a checkout's `compose.yaml` refuses the old store until
  it is migrated there, with `docker compose run --rm memory migrate`
  ([development](https://github.com/l7aromeo/user-memory/blob/main/docs/dev/development.md#a-server-built-from-the-checkout)).
- Codex's hooks are unchanged, so Codex needs no new approval.
- Restart Claude Code and Codex, and start new sessions. A session that was
  already running shows no change notice at its first prompt after the
  upgrade: snapshots from earlier versions are no longer read, so it takes
  a new one.

## New

- **Search ranks your project's memories by relevance.** A project memory
  still wins over a global memory that matches as well, but no longer over
  one that clearly matches better. Without a topic, project memories still
  come first. With semantic search on, search lists only the memories near
  the best match, instead of always the 20 nearest.
- **Keyword search understands word forms.** "releases" finds "release",
  rare words count for more than common ones, and a memory's title counts
  too. A topic word that names a category matches that category ("tool"
  finds tools). On the retrieval benchmark (`just retrieval-bench`), the
  mean reciprocal rank rose from 0.548 to 0.720 with keywords only, and
  from 0.413 to 0.865 with semantic search.
- **Search stays fast as the store grows.** The keyword index finds
  matches without reading every memory: on 100,000 memories a keyword
  search takes about 30 ms, where it took 720 ms. A server keeps each
  memory's current vector in memory, about 10 KB per memory at
  `qwen3-embedding:4b`'s full length, and compares the question with all
  of them at once.

## Fixed

- A rules write could replace an `AGENTS.md` you were saving at that
  moment, and lose part or all of your text. It now waits until the file
  has been unchanged for a second, and leaves a file that keeps changing
  for the next sync. To keep its own back-to-back writes from waiting,
  user-memory records each instruction file it wrote (its path, time, size
  and a hash of its text, never the text) in
  `~/.local/state/user-memory/instructions/`; uninstall removes the records.
- A server stopped answering while its writes waited for another process's
  turn on the store. It now keeps answering, reads included. A write queued
  behind a stalled one fails after 30 seconds with
  ``database is locked: another write in this process kept its write turn on the store for 30 s``
  instead of waiting without limit.
- A long-running server's memory grew with each search. On 100,000
  memories it now stays near 35 MB, where it climbed to 350 MB on macOS.
- A session could get wrong change notices after a build or setup used
  another store, or after a move to a server. Each session's snapshot now
  belongs to the store or server it came from.
